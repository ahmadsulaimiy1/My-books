# Known Issues Register

Every issue below was discovered during the audit "Phases" 2 through 4 of this project's
development history (chat-session phases — not to be confused with the **product roadmap**
phases in `docs/ROADMAP.md`, e.g. "Phase 2: English learning." Two unrelated numbering schemes
share the word "Phase" in this project's history; this register uses the audit-session
numbering, matching `docs/PHASE3_RELEASE_READINESS.md` and
`docs/PHASE4_BUILD_AND_DEVICE_VALIDATION.md`). This list only includes issues that are **still
open today** — anything found and actually fixed along the way (there were several — the
achievement-reset data-loss bug, silent TTS failures, hardcoded-string localization gaps, a
tashkeel-matching defect, touch-target/semantics gaps) is not repeated here; see each phase's
own document for that fix history if you need it.

| # | Discovered in | Severity | Description | Impact | Recommended fix | Release-blocking? |
|---|---|---|---|---|---|---|
| 1 | Phase 2 (Security audit); re-affirmed Phase 3 | **Medium** | The Room database (`sultan_arabic_ai.db`) is unencrypted plaintext SQLite. It holds learning history and certificate records containing user-entered recipient names (PII). | Anyone with filesystem access to a rooted/debuggable device, or a device backup that bypassed the current exclusion rule, can read this data in the clear. | Wire in SQLCipher's `SupportFactory` with a Keystore-generated passphrase (the concrete plan is already written in `docs/ROADMAP.md`'s "Security debt: database encryption" section) — this needs a real device/toolchain to verify, which is exactly what this handoff now provides. | **Yes, before any release handling real users' personal data at scale.** Not blocking for internal/developer testing, since a compensating control (backup exclusion) is already in place. |
| 2 | Phase 2 (Security audit); re-affirmed Phase 3 | Medium | Certificate `verificationCode` values have no cryptographic signature/HMAC binding them to the certificate's actual content (recipient, level, date). | A direct database edit could alter a certificate's content without invalidating its still-"valid"-looking code. Low exploitability today (no public verification endpoint exists to exploit), but becomes real the moment one ships. | Add an HMAC (keyed with a device- or app-level secret) over the certificate's content fields, stored alongside or derived into the verification code; verify it in `CertificateRepository.verify()`. | No — not blocking today given there's no public-facing verification surface yet. Blocking before any public certificate-verification feature ships. |
| 3 | Phase 3 (Security re-audit) | Low-Medium | Biometric login is a one-time, optional launch-screen gate. Nothing else in the app re-checks biometric/auth state; "Skip" or no enrolled hardware reaches all local data unconditionally. | Not a vulnerability relative to its own design (it was never built as a data-access lock), but it could be **mis-marketed** as "securing your data" when it doesn't. | Either (a) explicitly document it as a convenience/launch-gate feature only in user-facing copy, or (b) if real access control is wanted, redesign to re-prompt on resume-from-background or before sensitive actions (certificate export, etc.) — the latter is a real design decision, not a bug fix, and is out of scope for a "no architecture changes" handoff. | No. |
| 4 | Phase 1 (original build); re-affirmed every phase since | Low | `androidx.security:security-crypto` is pinned to `1.1.0-alpha06` — the only non-stable dependency in the project. This is a long-standing upstream situation (the library has had no GA release in years), not a regression introduced by this project. | Supply-chain/compliance risk for organizations with policies against alpha dependencies in production; functionally the API used has been stable for years in practice. | Monitor for a stable release; no drop-in stable alternative currently exists for `EncryptedSharedPreferences`. | No. |
| 5 | Phase 2 (Architecture audit) | **High** | Zero automated tests exist anywhere in the repository (`src/test`/`src/androidTest` don't exist) despite test dependencies being declared in `app/build.gradle.kts`. The domain layer (`domain/srs`, `domain/gamification`, `domain/quiz`) is pure Kotlin with zero Android imports — genuinely trivial to unit-test — making this a pure execution gap, not a design flaw. | No regression safety net for any future change. Every fix applied across Phases 2-4 was verified by manual code reading, not a test suite. | Write unit tests for the three `domain/` packages first (highest ROI, already-pure code); add Compose UI tests / Espresso instrumented tests for the core flows in the Device Test Playbook once a build exists to run them against. | Not blocking for a first internal build, but should block any release intended for broad/public distribution — "we manually read the code carefully" doesn't scale as a regression strategy. |
| 6 | Phase 2 (Architecture audit) | Low (today) / Medium (at scale) | No `@Index`/`@ForeignKey` declared on any Room entity's foreign-key-style columns (`lessons.bookId`, `vocabulary_words.lessonId`, `quiz_questions.lessonId`, `bookmarks.bookId`, `notes.bookId`). | Full-table scans on every filtered query; harmless at current seed-data scale (single-digit to low-double-digit rows per table), a real performance and data-integrity (orphan-row) risk once real book content is imported at scale. | Add `@Index` annotations and consider `@ForeignKey` constraints with `onDelete` policies before the PDF→lesson content-import pipeline (`docs/ROADMAP.md`) actually lands real-scale data. | No, not at current content scale. |
| 7 | Phase 2 (Performance audit); threading fixed in Phase 3, sizing never revisited | **Medium-High** | `PdfReaderScreen.kt` renders each page to an `ARGB_8888` bitmap at 2x the PDF's native point-size (~8MB for a typical A4-ish page), reallocated fresh on every page turn with no downsampling cap and no explicit recycling. | GC pressure / potential jank or OOM risk on low-RAM (≤3GB) devices during rapid page-turning. The main-thread-blocking part of this was fixed in Phase 3 (I/O moved to `Dispatchers.IO`); the bitmap-size-itself part was never addressed. | Cap the render scale (e.g. base it on actual display density/target width instead of a flat 2x) and/or explicitly `.recycle()` the previous bitmap before replacing it. | Recommend fixing before targeting low-RAM/budget devices specifically; not universally blocking. |
| 8 | Phase 3 (Accessibility re-audit) | Medium | Zero `WindowSizeClass`/adaptive-layout code exists anywhere — every screen is a fixed single-column phone layout. | Functional but visually sparse/oversized on 8"+/10"+ tablets; no width-based switch from `NavigationBar` to `NavigationRail`. | Genuine feature work (layout variants per width class) — correctly out of scope for every "no new features" phase since Phase 2.5, deliberately left here rather than fixed on the sly. | No, for a phone-first release. Yes, if tablet support is claimed in the store listing. |
| 9 | Phase 3 (Accessibility re-audit) | Low | Dark theme's `error` color (`SultanColors.Error`) against `surface`/`background` measures ≈2.4-3.0:1, below the 4.5:1 AA text threshold — but `MaterialTheme.colorScheme.error` (the theme role) is not actually bound to any text/icon anywhere in current screens, so this is latent, not active. | None today; would become a real contrast failure the moment any future screen binds text/icons to `colorScheme.error` directly (as opposed to the `SultanColors.Error` constant used directly elsewhere, which is a separate, unaudited-for-this-specific-pairing usage). | Give dark theme a dedicated `onError` color, or restrict `error`-role usage to non-text elements (borders, icon tint on a light background). | No. |
| 10 | Phase 3 (Arabic QA re-audit) | Low | `PdfReaderScreen.kt`'s header shows only `book.titleEn`, never `titleAr`, inconsistent with `LibraryScreen.kt` which shows both. | Cosmetic inconsistency, no functional impact. | One-line addition of a second `Text(book?.titleAr)`. | No. |
| 11 | Phase 3 (TTS scenario tracing) | Low | The voice-missing dialog's message ("`%s` voice data is not installed on this device") is precisely worded for the missing-voice-data case; when the actual condition is "no TTS engine exists on the device at all" (a different, rarer case, fixed to at least show *a* dialog in Phase 3), the wording is slightly imprecise even though the recovery actions offered are still correct. | Minor UX polish gap; the defect this was standing in for (silent failure) is fixed — this is about message accuracy, not functionality. | Branch the dialog copy on the specific `VoiceReadiness` reason rather than using one generic message for both `MISSING_DATA` and `ENGINE_UNAVAILABLE`. | No. |
| 12 | Phase 3 / Phase 4 (build verification) | **Critical** | No successful build of any kind (`assembleDebug`, `assembleRelease`, `bundleRelease`) has ever completed in any environment this project has been developed in. Root cause is confirmed to be network-policy-blocked access to Google's Maven repository in those specific sandboxed environments — the project's own configuration was independently re-verified as internally consistent (Phase 4) and is not itself implicated. | Every other verification activity (device testing, performance measurement, crash discovery) is blocked until this is resolved somewhere with real network/SDK access. | Build in Android Studio or a CI runner with normal internet access — see `docs/handoff/03_FIRST_BUILD_PLAYBOOK.md`. | **Yes — this blocks the entire release process by definition**, independent of every other item on this list. |
| 13 | Phase 3 / Phase 4 | **Critical** (direct consequence of #12) | Zero device or emulator testing has been performed for any of the six Android versions or device tiers identified as relevant (`docs/PHASE3_RELEASE_READINESS.md` §2-3). | Unknown whether the app actually runs, at all, anywhere. | See `docs/handoff/04_FIRST_DEVICE_TEST_PLAYBOOK.md`. | Yes, same reasoning as #12. |
| 14 | Phase 3 | High | Zero real performance measurements (cold start, warm start, PDF open time, quiz generation time) exist — not estimated-and-hedged, genuinely absent, because nothing has run to measure. | Cannot make or defend any performance claim publicly. | Use Macrobenchmark or simple timestamp logging once a real build exists. | Recommend resolving before any performance claim in marketing/store listing; not a hard release blocker for functionality itself. |
| 15 | Original build (not a later-phase audit finding, but still open) | Medium | Seeded lessons/vocabulary in `data/seed/ContentSeeder.kt` are representative starter content in the structural style of the SULTAN curriculum, explicitly documented as **not** a transcription of the bundled book (automated PDF text extraction wasn't available in the original build environment). | The app's actual learning content is a small placeholder set (3 lessons, 6 vocabulary words), not the real curriculum. | Build the PDF→lesson import pipeline described in `docs/ROADMAP.md` to extract real content from the bundled book. | **Yes, for any release positioned as delivering the actual SULTAN Book 2 curriculum** — not blocking for an internal architecture/functionality-only build. |
| 16 | Engineering briefing review (Phase 5) | Low | `QuizGenerator` generates both `MULTIPLE_CHOICE` and `FILL_IN_BLANK` question types and stores both, but `QuizScreen.kt` filters to only render `MULTIPLE_CHOICE` (`QuizScreen.kt:72`). | Fill-in-blank questions are silently generated and persisted but never shown to the user — possibly intentional (UI for that type was never built) or possibly an oversight. Needs a human product decision, not a unilateral fix. | Either build the fill-in-blank UI, or stop generating/storing that type until there's a UI for it. | No — flagging for a decision, not treating as a defect with an obvious right answer. |
